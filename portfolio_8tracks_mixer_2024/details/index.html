Project in depth

Audio data engineering and applied ML on AWS

Developed audio-analysis software, AWS processing components and interactive demonstrations for 8tracks.com / mixer.fm. The work combined signal processing, pretrained machine-learning models, track metadata and cloud engineering to explore how listeners could find music by its sound, mood and musical characteristics. It also included the architecture for a future recommendation service.

Client / context
8tracks.com / mixer.fm

The problem and my contribution

An audio catalogue contains information that titles, artist names and existing tags cannot fully describe. Tempo, instrumentation, vocal presence, mood and musical style provide additional ways to organise and discover tracks.

As Data Architect / Head of AI, I worked across audio processing, model integration, data storage, AWS infrastructure and technical demonstrations. The wider project involved an existing audio collection of approximately 150–160 TB. My development work produced processing components and demonstrations, while the recommendation service was a separate architecture and development proposal.

AWS processing and infrastructure

Developed Python Lambda components to access audio files and machine-learning models in S3, stage them on EFS and write extracted features to PostgreSQL. The S3 loader paginated object listings, copied files through temporary storage, placed them on EFS and removed temporary copies after transfer.

Defined the environment with AWS SAM and CloudFormation. This covered Lambda functions, the EFS file system and access point, RDS PostgreSQL, VPC networking, public and private subnets, routes, a NAT gateway, service access and the permissions needed by the processing components.

  • Separated file loading, feature extraction and environment checks into distinct Lambda handlers.
  • Used EFS to make Python dependencies, audio files and model files available to the Lambda runtime.
  • Added checks for EFS access and Python imports to diagnose cloud execution problems.

Build automation and a reproducible development environment

Prepared an AWS CodeBuild project and build specification to create the Python environment on EFS, install the required libraries and copy models and audio assets from S3. Defined the build environment alongside application infrastructure so that its dependencies and cloud resources could be managed together.

Also prepared a Docker environment for local feature-extraction development, including Essentia compilation, audio-processing dependencies, PostgreSQL connectivity and resource monitoring.

  • Python, NumPy, pandas, boto3, psycopg2, TensorFlow and Essentia dependency setup.
  • Version-controlled infrastructure definitions, processing code and build instructions.
  • Configuration of runtime paths for packages, models and audio files.

Turning audio signals into structured features

Used Essentia MusicExtractor to calculate low-level, rhythmic and tonal characteristics. Converted NumPy arrays and scalar types into JSON-compatible values and prepared structured records that could be combined with track metadata.

The extraction work covered both detailed feature exports and a smaller set of selected fields for the AWS component. Early experiments also used simple rules to turn numerical features into readable labels for energy, danceability and mood.

  • Spectral centroid, flux and rolloff; zero-crossing rate; MFCC-based summaries.
  • Tempo, beat positions, loudness and rhythm statistics.
  • Musical key and scale, chord strength, harmonic pitch-class summaries and tuning frequency.
  • Means, variation and other summary statistics for comparing tracks and preparing analytical outputs.

Genre, style and danceability

Integrated pretrained audio models through Essentia's TensorFlow interfaces. Audio was loaded as a mono signal at the sample rate required by each model, converted into embeddings and passed to the relevant classifier.

For music style, used Discogs EfficientNet embeddings and the 400-class Discogs genre/style model. Aggregated segment-level classifications to identify dominant styles and separated the resulting style and substyle labels. A further classifier produced the three strongest MTG-Jamendo genre scores by averaging predictions across the track.

For danceability, used VGGish embeddings and a pretrained danceability classifier. Calculated a track-level score from the proportion of audio segments classified as danceable. These results were combined with signal-processing features in the AWS extraction component.

A broader set of audio-classification experiments

Developed individual inference experiments for a wider range of musical characteristics. These scripts loaded pretrained models, processed sample audio and translated numerical outputs into readable labels or scores so that their usefulness for music discovery could be assessed.

The work involved integrating and interpreting existing models, including Discogs EfficientNet, VGGish and MusiCNN embeddings. It provided a practical basis for choosing which characteristics belonged in track metadata and which required further evaluation.

  • Mood and theme: happy, sad, relaxed, aggressive and party-related characteristics, MTG-Jamendo mood/theme tags and MIREX mood categories.
  • Arousal and valence: translating model outputs into levels of intensity and positive or negative emotional character.
  • Instrumentation and sound: instrument tags, acoustic/electronic character, vocal versus instrumental content, timbre and tonality.
  • Additional experiments: audio-event recognition with YAMNet, music approachability, engagement and general music tags.

Metadata, PostgreSQL and processing measurements

Matched extracted audio features to existing track metadata, including artist, title, release, year, duration and catalogue references. Implemented PostgreSQL tables for feature records and classifications, JSON exports for inspection, handling of missing values and bulk inserts for local processing.

Added execution-time and resource measurements with psutil, including CPU and memory information. In the genre-processing work, loaded the embedding and classifier models once and reused them across files, rather than reloading them for every track. Stored processing measurements separately from the musical results to make development runs easier to inspect.

Analysis over time and an interactive audio demonstration

Explored how musical characteristics change during a track. Developed TempoCNN experiments for global and local tempo estimates, with segment boundaries and associated values stored in PostgreSQL. Also prepared pitch-tracking experiments with CREPE and source-separation experiments with a pretrained Spleeter model for vocals, drums, bass, piano and other sound sources.

Built a browser-based audio demonstration with a waveform, timeline and play, pause and stop controls using WaveSurfer.js. A Python HTTP service read segment features from PostgreSQL and returned them as JSON. The interface selected the relevant segment during playback and displayed its tempo information, making the analysis easier to understand while listening.

Librosa analysis and external metadata experiments

Developed a Librosa notebook that converted M4A files for analysis, extracted tempo, chroma, energy and spectral features, and joined them with track metadata. Added spectrograms, chromagrams and tempograms, function timing and Excel exports to compare and inspect the results.

Built a separate Flask experiment around the Spotify API, including an OAuth callback, track lookup and helper functions for track metadata, audio features and audio analysis. This explored an additional source of descriptive information alongside features calculated directly from the audio.

Recommendation architecture and next-stage development

Designed a proposed recommendation service combining audio characteristics, collaborative filtering, listening history and explicit feedback. The design addressed sparse interactions, new tracks and new listeners, candidate selection, recent listening context and the effect of skips and repeated plays.

Separated the responsibilities for feature generation, model execution, search, recommendation delivery, feedback collection and evaluation. Considered relational storage, object storage, search indexes and fast interaction stores according to their purpose, and proposed a staged roadmap for retries, processing checkpoints, monitoring and ranking evaluation.

The combined contribution connected hands-on audio analysis with the engineering and architecture needed to turn model outputs into useful music-discovery features.

Recommendation design: listening context and candidate selection

The proposed service went beyond matching a track to a genre label. It combined collaborative candidates with audio characteristics and recent listening context, including the last few tracks, time-of-day context and feedback such as skips, replay and playlist additions.

The design examined sparse interaction histories and cold-start cases for new tracks or listeners. It considered an initial matrix-factorisation or simpler neural approach, with staged expansion and evaluation rather than assuming that the most complex model should be the starting point.

For user-created tags, the design considered disagreement between a label and measured audio characteristics. Proposed handling included confidence weights, community agreement, embeddings and similarity comparison.

Proposed service boundaries, search and feedback

Separated recommendation delivery, feedback collection and search into API responsibilities. A natural-language music request was mapped conceptually through entity/mood interpretation, feature search and personalisation.

The architecture considered relational storage for audio features, a fast store for current interaction context, a search index for descriptive retrieval and a historical analytical store. It also examined how initial indexing and later updates would be handled.

The administrator view was planned around processing status, resource use, model behaviour, alerts and controlled reruns. These are design outputs for the next stage of the service, alongside the implemented audio-processing components described above.

Planning large-catalogue processing and evaluation

The proposed batch workflow included paginated object discovery, batches defined by count or file size, checkpoints, remaining-runtime checks, pause/resume, retry and escalation. Those controls address the practical task of progressing through a large catalogue without treating each development demonstration as a full-catalogue run.

The model-evaluation plan connected ranking quality with listening behaviour and the usefulness of extracted features. The project joined code-level experiments with an explicit design for operating and evaluating a larger music-discovery service.
