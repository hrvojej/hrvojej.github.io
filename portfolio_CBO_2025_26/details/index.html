Central Bank of Oman — architecture, prototypes and finalist evaluation

Served as Lead Data Architect and Project Manager for the NEOS team’s pre-contract work on the Central Bank of Oman Data Collection Platform and Data Lake opportunity. Developed a working demonstration application, supporting prototypes and an on-premises lakehouse proposal. The team reached final-stage evaluation, including a visit by the bank’s delegation to Zagreb, where I presented my work and relevant project references.

Role, scope and outcome

Led data architecture and coordinated the technical work during solution preparation, prototyping and evaluation. Worked with the NEOS team and its Oman partner to connect the bank’s reporting needs with the proposed data platform, application workflows and delivery approach.

The engagement covered extensive preparation before an implementation contract: architecture documents, software and hardware assumptions, demonstration scenarios, a web application and presentations. The team reached the final evaluation stage and hosted an in-person reference visit by a Central Bank of Oman delegation in Zagreb.

The engagement did not progress to contract award or production implementation. The work described below consists of delivered prototypes, solution design and technical evaluation activities.

From regulatory submissions to usable analytical data

Worked through the relationship between the Data Collection Platform and the lakehouse: regulated institutions submit returns, the platform identifies the institution and reporting period, checks the submission and tracks its state, and accepted data becomes available for governed analysis.

Developed the proposed interaction between online forms, structured files and supporting documents. Defined stable field identifiers, explicit schema versions, reference lists and rules for resubmitting corrected data. The aim was to make collection, validation, ownership and subsequent analysis part of one understandable process.

The design accommodated different levels of submitting institutions’ technical maturity, with file-based reporting and a gradual route toward forms and APIs.

A working web demonstration application

Built a Python/FastAPI backend with SQLAlchemy and SQLite, together with a Vue 3 frontend using PrimeVue, Vite and Tailwind CSS. The application supplied interactive workflows backed by a relational demo database, alongside presentation prototypes and scenario-specific interface mockups.

Created views for licensed institutions, return management, submissions, ad-hoc requests, reference material, notices, messages and institution-facing reporting. The application helped stakeholders see how the proposed platform would be used, beyond diagrams of its storage and processing components.

Regulatory-return configuration and ownership

Modelled return definitions with codes, names, descriptions, reporting frequencies, effective dates and due dates. Linked a return to the institutions expected to submit it, its fields and the validation rules configured for it.

Added responsible and accountable contact fields to connect each reporting requirement with business ownership. The demonstration interface supported defining, editing and publishing return configurations, with field labels, data types, required flags and display order.

Implemented storage and editing of validation-rule definitions in the demonstrator. The wider architecture specified structural and business validation, including cross-field and cross-table checks; that full production validation framework remained part of the proposed solution.

Submission revisions and comparisons

Implemented submission records linked to the return template, reporting institution and reference period, with individual field values held in related records. A revised submission created a new version while marking the earlier submission as superseded.

Built comparison endpoints and interface views that showed values from two versions and identified changed fields. Included selection of the previous version for the same institution, return and reporting period.

Added prototype approval and rejection transitions and institution-specific submission lists. These workflows made correction and resubmission tangible during the evaluation, while the architecture described the stronger audit and access controls required for production.

Ad-hoc requests, notices and communications

Developed ad-hoc request models with ordered questions, response types, optional choices and required-field flags. Linked each request to target institutions and provided publication controls.

Built reference-item and notice workflows covering descriptions, effective dates, document links and applicable institutions or returns. Added messages with sender information, subject, body, read state and links to the relevant reporting context.

These components extended the proposed portal beyond file submission to the supporting communication and administration needed around regulatory reporting.

Lakehouse and payment-analytics demonstrations

Prepared a data-lake browser to illustrate structured, semi-structured and unstructured data categories, folders and representative file types. This was an illustrative view of the proposed lake organisation.

Built payment-analytics screens using generated demonstration data to show transaction volumes and values, channel comparisons and changing time-series views. Chart.js supported the visual presentation.

The lake browser and payment stream were simulated. They illustrated the intended user experience and analytical questions without implying a connection to the bank’s live systems or a deployed production lakehouse.

Proposed on-premises platform architecture

Designed an enterprise lakehouse proposal spanning platform operations, object storage, table formats, batch processing, SQL access, orchestration, transformation and governance. The design kept the platform and its control planes within the bank’s own infrastructure.

The proposed stack combined OpenShift, MinIO, Apache Iceberg, Dremio, Apache Spark, Astronomer/Apache Airflow, dbt, Apache Kafka and Collibra. Defined their respective responsibilities and the relationship between the technical table catalog, analytical access layer and business governance catalog.

Specified source-aligned landing, processing and analytical zones, with batch and streaming ingestion patterns, quality controls and publication of datasets for reporting. Described how database transformations, orchestration events and catalog information would contribute to lineage.

Security, operations, sizing and delivery planning

Developed the proposed primary/disaster-recovery arrangement, workload separation, role-based access, encryption, audit logging and retention controls. Connected platform operation with controlled releases, Git-based configuration and repeatable deployment of processing jobs.

Prepared capacity assumptions, hardware bill-of-materials inputs and indicative licensing/subscription estimates. Linked these to the anticipated processing and operating model so that technical choices could be discussed alongside their commercial implications.

Outlined a phased approach covering platform foundations, initial use cases, broader governance and scaling, and subsequent operations. Coordinated technical explanations and follow-up material during the evaluation. The infrastructure and licensing material was proposal work, rather than a purchased or deployed production configuration.

Migration from document-based reporting

Developed detailed submission options for wide tables, multi-sheet workbooks and multi-file reporting packages. Specified how field identifiers, schema versions, metadata and file manifests could provide consistent rules across those formats.

Designed a gradual route from PDF-heavy reporting toward structured companion files, online forms and APIs. Supporting documents remained associated with the submission, while structured values could be checked and processed consistently.

Defined clear feedback for schema and business-rule failures, versioned corrections and traceability from a reporting requirement to the received data. This work connected data architecture with practical reporting procedures and the application interface.

Presentations and the delegation’s visit to Zagreb

Prepared and participated in the technical presentation in December 2025, including customised demonstrations of regulatory returns, validation configuration, data-lake organisation and payment analytics.

During the final evaluation stage, participated in the bank delegation’s visit to Zagreb in February 2026. Presented my own work and relevant experience from Raiffeisenbank Austria d.d., Croatia (RBA), the Agency for Commercial Activities (AKD) and other projects, together with colleagues from NEOS.

Contributed to the technical programme for the reference visit, connecting ingestion, data quality, processing, reporting, orchestration, security and operational resilience with the relevant specialists. The visit and finalist-stage evaluation were significant outcomes of the bid preparation.

What this engagement demonstrates

Combined lead architecture and project coordination with hands-on application development, prototyping and explanation of complex technical choices to client stakeholders.

The contribution spanned the full proposed journey from an institution’s reporting form to governed analytical data: domain modelling, interaction design, database-backed prototypes, platform design, sizing and a phased delivery proposal.
