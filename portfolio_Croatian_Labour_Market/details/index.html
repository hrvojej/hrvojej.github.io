Project in depth

National labour-market and education analytics

Served as Data Architect and Lead Data Engineer for Croatia’s national labour-market and education analytics platform. Migrated and developed database processing, institutional data collection and analytical datasets that connect education with employment, unemployment and employer demand.

Client / context
Croatian Ministry of Labour, Pension System, Family and Social Policy

National scope and my responsibility

Held the combined roles of Data Architect and Lead Data Engineer. The work connected national employment and education sources into a common analytical platform, covering database processing, recurring collection, historical imports, shared classifications and education-to-employment analysis.

As lead data engineer and developer, migrated the existing analytical processing to Microsoft SQL Server and developed the collection, import and transformation workflows around it. The work covered substantial SQL procedure logic, source formats, Python and C# collection scripts, reference classifications, historical loading and operational documentation.

Migration and redevelopment of the analytical processing

Migrated the existing platform’s data processing to Microsoft SQL Server, adapting database procedures and the surrounding import and transformation scripts. This required preserving the meaning of the analytical data while making the loading and enrichment sequence work in the target database.

Organised processing into source-specific import procedures followed by enrichment of the shared analytical tables. The procedures accepted reporting-period parameters so that the same processing could be used for a monthly refresh or a historical rebuild.

Kept separate procedures for older and newer pension-insurance record structures, unemployment and employer-demand data, school records and higher education. The resulting platform combined the recurring institutional feeds with the SQL logic needed by the national analytics portal.

The core data sources

Each source required a different delivery contract and schedule. The engineering preserved those differences during ingestion and reconciled them in the analytical layer.

Pension-insurance data: from SFTP files to SQL Server

Developed Python processing to identify the required monthly delivery, retrieve it from SFTP, convert the text to UTF-8, read it into a pandas DataFrame and prepare the values for database loading. The process generated the period-specific import table and loaded the supplied records.

Handled the older 2018–2020 record structure and the revised structure used from 2021. Separate loaders and import procedures allowed historical data and later monthly deliveries to enter the same analytical workflow without assuming that their schemas were identical.

The records covered demographic and qualification attributes, occupational codes, place of work, contract type and employer/activity identifiers. Source-specific preparation included conversion of the age field before import.

Employment-service APIs and historical reloads

Implemented separate Python API workflows for registered unemployment and employer demand. Each created a monthly import table and loaded the corresponding response into SQL Server.

Provided both monthly collection and loaders accepting a range of years and months. This made it possible to populate historical periods, repeat a delivery or rebuild a selected portion of the analytical history.

The richer employer-demand schema included occupation, location, required education, language and IT skills, professional skills, experience, employment type, working hours and the number of requested workers. Preserving these fields made the data useful beyond a single vacancy count.

Higher-education and school-data processing

Built the monthly Student Rights Information System workflow around a Python API client and period-specific raw tables. Prepared student, programme, institution and enrolment attributes for a dedicated higher-education analytical dataset.

Developed the annual eMatica import workflow for primary- and secondary-school records. Used C# / LINQPad export scripts with the eMatica service client, followed by Python loading and SQL Server processing. Prepared individual school-year imports and a multi-year export workflow.

The school-data collector traversed institutions and their organisational units, requested pupil records for the selected school year, and flattened nested institution, programme, class and enrolment structures. Loaded reference lists for programmes, counties, countries, places, classes and school years; used these to add readable descriptions to the export.

Kept the different refresh frequencies explicit. Monthly employment and student updates and annual school deliveries could use the same platform without pretending that every source arrived on the same timetable.

Raw imports and analytical database layers

Separated minimally modified source records from the analytical tables. Raw tables retained their source and reporting period; the analytical database combined those imports with classifications, derived fields and the transformations needed by the portal.

The main labour-market table brought together pension-insurance records, registered unemployment and employer demand. Separate analytical tables served higher education and primary/secondary education, rather than forcing unrelated record types into one wide table.

Implemented and documented SQL Server stored-procedure calls for source loading, synchronisation and subsequent enrichment. Historical loops over year and month made the processing sequence explicit and repeatable.

Connecting education records with the labour market

Built SQL datasets connecting school and higher-education records with a selected monthly employment/unemployment snapshot through the person identifier. These linked datasets supported analysis of education histories alongside later labour-market status.

Prepared separate datasets for primary and secondary education and for undergraduate, graduate and postgraduate study. Retained institution, programme, qualification sector, location and reporting dates so that the educational context was available alongside the labour-market record.

The SQL scripts included earlier and later education observations, grouping, joins and unions to prepare the comparison datasets. The accompanying career-tracking design described how these education stages could be assembled around a person-level analytical record.

This extended the project beyond collecting institutional feeds: the data engineering made it possible to investigate how education and qualifications relate to employment across Croatia.

Occupations, qualifications and geographic reference data

Connected operational records to National Classification of Occupations codes (NKZ), mappings between the 1998 and 2010 classifications, and Croatian Qualifications Framework sectors and subsectors (HKO). Reference data also included education levels, employment-contract types and territorial codes.

The transformation work resolved differences between source codes and analytical categories. It combined cleaning, type conversion, reference lookup and calculated fields so that reports could compare records using consistent occupational, educational and geographic groupings.

Changes to reference mappings could affect historical results. Documented the need to repeat enrichment for earlier periods when classifications changed, keeping the implications of a reference-data update visible to the operating team.

Scheduling and operational handover

Connected scheduled execution with Windows batch launchers and Python scripts. The employment and unemployment workflows were scheduled monthly, while the annual school-data import followed its own cycle.

Added operational email notifications in the monthly collection scripts for missing source deliveries and completed imports. The messages identified the reporting period and, where available, the imported record count, helping operators spot an incomplete monthly refresh.

Prepared operational instructions describing delivery conventions, source schemas, script responsibilities, raw-table creation, stored-procedure execution and the order of the loading and enrichment steps. Included examples for loading individual months and rebuilding longer periods.

These instructions made the dependencies between source retrieval, raw imports and analytical refresh clear, helping subsequent maintainers operate the platform and investigate incomplete periods.

Working through source-quality and integration differences

Worked with records arriving through APIs, SFTP and source files, including interfaces routed through the government service bus. Handled different record versions and delivery formats within the processing design.

The integration work also had to account for missing programme identifiers and differences between agreed exchange formats and actual deliveries. Programme identifiers were needed to associate education records with qualification sectors; an absent identifier could therefore limit later analytical classification.

Kept implemented processing distinct from proposed later sources. The core workflows described here are employment, unemployment, employer demand, higher education and school education. The historical integration plan also discussed financial-agency and insured-person-register data, with different readiness states.

Result and relevance

Created the data-processing foundation for a national analytical view connecting the labour market with education. The delivered work joined collection, historical loading, database transformations, classification enrichment, scheduling and technical handover.

This project demonstrates practical integration across public institutions: understanding the meaning of their records, accommodating changes in source structures and turning recurring deliveries into a maintainable analytical platform.
