Engineering objective and scope

The project addressed a synchronised control system for an advanced distribution network, with reliability and robustness in real time. The wider concept considered distributed generation, storage, charging infrastructure and electric vehicles as participants in grid services.

My responsibility was the data and software path: receive measurements, decode protocol messages, serialise records, synchronise streams, calculate rules, persist results and connect those calculations to a PLC reaction. It joined enterprise-style data engineering with the timing and interoperability demands of operational technology.

The achievement: fast processing with a defined measurement boundary

The documented result was approximately 50 ms latency for processing and result availability, compared with a project requirement below two seconds. PMU measurements arrived every 20 ms; this is a sampling interval and is distinct from processing latency.

The processing-latency figure describes the documented data-processing/result path. The reactive PLC component was a separate part of the implementation, with device response considered separately from data availability.

PMU ingestion and protocol-level diagnosis

Implemented Python socket applications that received PMU (Phasor Measurement Unit) measurements over TCP. Reassembled binary/hexadecimal message bytes into protocol frames and converted them into structures suitable for downstream processing.

Handled C37.118 command, configuration and data frames. Extracted device identifiers, timestamps, status values, voltage and current phasors, frequency, rate of change of frequency, and analogue/digital values.

Diagnosed a pyPMU/Python Synchrophasor Module issue where simulator and tinyPDC examples worked but a real device stream failed. Investigated configuration-frame success followed by an unknown-message error on data frames, using captured network traffic and Wireshark/PCAP evidence. The defect and resolution were documented in the project material.

Kafka platform and a consistent data contract

Installed and operated a Kafka platform on an Ubuntu server. The Docker Compose environment included a broker, ZooKeeper, Schema Registry, Kafka Connect, REST Proxy, ksqlDB, Control Center and a separate PostgreSQL container.

Developed independent Python producers for two PMU inputs. Transformed protocol frames into Python dictionaries, serialised them with Avro, and maintained consistent types through Java stream-processing objects and PostgreSQL destination tables.

Preserved original timestamps and introduced a rounded timestamp for synchronisation. Included source/device identifiers and the values required to trace message sequences and reproduce calculations.

Synchronising measurements before applying rules

Built a Java application with the Kafka Streams API to join the two PMU streams. Small differences in the least-significant timestamp digits could otherwise cause matching measurements to be missed; the rounded timestamp served as the join key.

Published the joined measurements to a separate stream. A second Java/Kafka Streams application calculated phase-angle differences and related voltage values over synchronised observations. Join logic and rule calculation remained independent applications, making the processing responsibilities explicit.

Results, SQL triggers and the last mile into OT

Created Kafka Connect sinks for raw measurements, joined streams and calculated results. Maintained compatibility between Avro schemas, data types and PostgreSQL tables.

Developed SQL triggers to process and expose stream-processing results in tabular form with low delay. A separate reactive Java application connected rule outputs to PLC triggering for network equipment.

This final step is the IT/OT interface: a result produced by the data platform becomes an input to operational control. My contribution connected the software/data path with that device-level reaction.

Operational handover and observability

Prepared an ordered startup procedure covering the platform, database, connectors, producers, join application and rule application. The development environment used Python virtual environments, Java, Gradle builds and separate tmux sessions.

Documented checks for Docker services and logs, Kafka topics and live records, connector states and configurations, and database contents, sizes and permissions. Added an hourly cron retention procedure for raw, joined and result tables.

The operating instructions include later maintenance edits. They support the technical description without changing the stated 2020–2022 project period.

Research direction

Spark analytics and predictive ML were investigated as possible extensions. The implemented reference described here is the Python, Java/Kafka Streams, PostgreSQL and PLC path.
