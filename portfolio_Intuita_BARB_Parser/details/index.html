Project in depth

A modular Python parser for audience-measurement data

Developed a modular Python parser and PostgreSQL processing prototype for BARB audience-measurement data at Intuita UK. The work translated complex fixed-width file specifications into record layouts, parsing routines and relational tables for viewing activity, advertising spots and the reference data needed to interpret them.

Client / context
Intuita Consulting, UK · BARB Audiences data formats
Period
During the Intuita engagement · September 2022 – February 2024

Three complementary audience-data formats

Built separate processing modules for Panel Viewing files (DSP01), Daily Spot Data files (DSP04) and BARB Master files (DSP14). A common folder processor reads each file's header to identify its format and sends it to the corresponding parser.

The implementation separates record definitions from file processing. Each definition describes the field names, positions, widths and record keys, together with the PostgreSQL table used to store that record.

Reference data for channels, panels and services

The Master-file module models the reference information needed to interpret audience and advertising records, including reporting stations, station relationships, reporting panels and their relationships.

  • Channel names, codes, reporting periods, transmission formats and reporting flags.
  • Sales houses, broadcast groups and audience categories.
  • Commercial-duration factors, panel and geographic factors.
  • Video-on-demand providers, services and types, device types and online players.

Panel viewing, households and devices

The Panel Viewing module includes layouts for household characteristics, television sets, individual panel members, response and weighting information, online devices and viewing sessions.

Separate viewing layouts cover panel members and guests in the PV2/PVE and PVX/PXE families. They retain session timing and duration, station and platform identifiers, playback information, video-on-demand context and the applicable viewer or guest information. Related record codes are mapped to their shared layout.

Advertising spots and audience measures

The Daily Spot module extracts transmission dates, reporting panels and stations, advertising-break and spot timings, commercial identifiers, campaign references and surrounding programme information.

Its main record layout includes live and consolidated audience values for 71 audience categories. Additional layouts capture station-log information and the file trailer. Insert/delete indicators are retained as source fields for subsequent processing.

From fixed-width text to relational records

Implemented field extraction using the positions and lengths defined for each record type. The processors read files line by line and select the appropriate layout from the record-type code.

Designed separate PostgreSQL schemas for the three file families, with header tables, record tables and record-type lookup tables. Header identifiers associate inserted records with their source-file metadata, while processing timestamps record when rows are handled.

The prototype uses parameterised SQL values and upsert statements built from the declared record keys. Source fields are retained as text, preserving codes and fixed-format values before later analytical conversion.

Batch processing and development diagnostics

Added a folder-level runner and individual command-line processors so that the three formats can be handled through the same workflow. Processing runs sequentially, with progress messages, counts by record type and elapsed-time reporting.

Added a Master-file trailer-count comparison and SQL inspection queries to support verification during parser development. The implementation was developed as a processing prototype, with diagnostic output for inspecting record handling.

Preparing the warehouse integration

The work brought together format interpretation, Python development and relational modelling, making the audience-data structures explicit and preparing them for further ETL work.

Prepared a subsequent ETL architecture proposal using AWS S3 and Snowflake. This was the proposed next stage after the parser and processing prototype.

How the prototype separates dispatch, layout and storage

The dispatcher identifies the supported file family and invokes its corresponding processor. Record-layout metadata supplies the field positions and lengths for fixed-width interpretation, while the processor associates the records with the file header and prepares database writes.

The reviewed implementation defines 35 record layouts across three supported file families. The daily-spot layout includes paired live and consolidated measures for 71 audience categories, illustrating why a metadata-driven parser is more manageable than hand-writing an unrelated parser for every output field.

The PostgreSQL prototype uses record keys and header references to organise parsed data. Diagnostic counts and summaries help inspect the parsing work; the subsequent AWS S3/Snowflake pipeline remained a proposed next stage.
