Databricks engineering: workshops, labs and team enablement

Authored and delivered a two-day Azure Databricks Data Engineering workshop for NEOS, part of KONČAR Group, on 20–21 April 2026. Developed seven teaching modules, runnable banking examples and separate follow-up programmes for data engineers and DevOps/platform engineers.

Programme design and delivery

Prepared approximately two full days of instruction for a planned group of ten data engineers. Combined explanations, demonstrations, guided notebook work, independent exercises and discussion of the results. The material connected practical engineering with Databricks Data Engineer Associate and Professional certification topics.

The live workshop and the broader learning package had different scopes. I adapted the two-day plan to the available NEOS environment and retained more extensive source-simulation, PostgreSQL and infrastructure exercises as follow-up work. This allowed the workshop to focus on the platform while giving participants a substantial route for continued practice.

Preparing the Azure Databricks environment

Prepared setup and verification instructions for a Premium workspace, Unity Catalog and an ADLS Gen2 landing area. The lab configuration used Databricks Runtime 16.4 LTS, Photon and a single-node compute configuration with automatic shutdown.

Separated participant tasks from the permissions and infrastructure that NEOS DevOps needed to provide. Workspace access, storage access, compute availability and catalog permissions were prerequisites to running the notebooks, so setup checks were part of the learning material.

Organised notebooks, Python labs, setup instructions and a browsable HTML learning site. Reference projects included Databricks Bundles, a banking lakehouse and a separate dbt banking example.

A banking demonstration that produces inspectable results

Developed an educational flow from synthetic source preparation to layered transformations, suspicious-event indicators, validation and a case-review queue. Prepared an instructor learning path and execution notes so the demonstration could be explained and checked at each stage.

One recorded run produced 5,034 demonstration fraud alerts, including 1,560 critical alerts, together with 121 login anomalies and 250 high-risk items. The case queue contained 1,560 records. These are outputs from synthetic educational data, useful for checking execution and interpretation.

The material also records the score and precision of that particular scenario. It provides a way to discuss why generating an alert and demonstrating a reliable operational model are different tasks; it is not a benchmark for a deployed bank fraud system.

The dbt example: building, diagnosing and verifying

Built a batch workflow with dbt models and tests, a run-summary task, a conditional branch and a case queue. This joins model development with the execution and handover steps needed to operate the example.

Diagnosed a TABLE_OR_VIEW_NOT_FOUND failure in publish_run_summary. The cause was a duplicated schema name, and I corrected the generate_schema_name macro before rerunning the workflow.

The subsequent run completed with 29 PASS tests, zero warnings and zero errors, and satisfied the critical condition for continuing the workflow. Its synthetic outputs included 135 alerts, 15 critical items, 95 items for manual review, 23 login anomalies and a queue of 15 cases. The example therefore includes a real failure, its cause, the correction and evidence of the rerun.

Follow-up data-engineering assignment: four source domains

Created a separate self-paced package with introductory guides 01–09 and assignments 10–19, an offline web view and launch scripts. It leads from local prerequisites to a connected end-to-end data workflow.

The local banking simulator uses PostgreSQL schemas with linked entities. Prepared semi-synthetic data using SDV/HMA concepts, a deterministic seed and preservation of primary/foreign-key relationships across the schemas.

Testing incremental changes with T1, T2 and T3

Defined three successive snapshots for practising incremental processing. Later snapshots include approximately 5% changed records and 10% new records, so participants must deal with updates as well as inserts.

Prepared Parquet export using pandas and pyarrow and upload to a Unity Catalog Volume using the Databricks SDK. The downstream assignment uses Auto Loader for Bronze ingestion, MERGE and SCD2 patterns in Silver, and business marts in Gold, including daily transaction facts.

This makes the effect of a source change visible through the layers. The task goes beyond loading a static file: participants must maintain keys, apply changes and produce consistent business outputs over successive runs.

Acceptance criteria for independent work

Specified data checks, CHECK/expectations rules and a quality criterion of at least 95% for the assignment. Added an optional streaming fraud/AML scenario for further practice.

Required a private Git repository with meaningful commits, a README that explains how to repeat the run, mapping to certification topics and evidence that the acceptance criteria were met. Feedback was organised through issues, pull requests and instructor review.

The package distinguishes the defined acceptance criteria from each participant’s eventual achievement. It supports learning at the participant’s pace without presenting every optional extension as part of the two-day workshop.

Promotion, diagnosis and engineering ownership

Prepared a small demonstration workload for practical deployment. DEV execution is tied to the learner’s available permissions; TEST, UAT and PROD are addressed through a promotion plan, evidence and approval points.

The incident runbook asks the engineer to investigate a failed deployment or run, choose a repair or rollback and show the result of the repeated check. Monitoring guidance includes alternatives when a participant lacks administrative access.

This connects the data engineer’s business logic with the platform team’s delivery responsibilities. It also makes clear which tasks require a cloud administrator or IAM owner.

Validation and reusable teaching output

Documented material checks and subsequent fixes. The earlier April 18 review recorded 28 passing checks out of 29 tested, one failure and one separately skipped check; the later dbt example had 29 passing tests after correction. These are separate validation records.

The published workshop site brings together the teaching sequence, labs and follow-up material. The result is a reusable engineering curriculum with concrete inputs, expected outputs, execution evidence and a way to continue learning after the live sessions.
