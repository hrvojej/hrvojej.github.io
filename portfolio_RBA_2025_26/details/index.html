From legacy ETL to an open lakehouse

Designed a lakehouse migration framework and built reverse-engineering and AI orchestration tools for Raiffeisenbank Austria d.d., Croatia. The work connected legacy ETL analysis with dependency-ordered dbt development, actual SQL execution and comparison against existing bank outputs.

Three connected engineering assignments

As Data Architect / Principal Data Engineer from September 2025 to February 2026, I worked on three connected problems: defining how the warehouse should move to a lakehouse, recovering the logic hidden in the existing ETL estate, and automating conversion while retaining checks against the original results.

The migration framework addressed an existing estate of approximately 4,300 ETL mappings, 1,800 landing tables and more than 20 source systems.

Understanding the existing processing before changing it

Business logic was distributed across Oracle Data Integrator, Oracle Job Chains, IBM DataStage, PL/SQL and database views, with Oracle and PostgreSQL in the wider warehouse environment. A report could depend on transformations in several tools and layers, so a list of tables alone was insufficient.

I analysed landing, staging, data-quality, core, view and reporting relationships. The important questions were where a target value originated, which expression produced it, which intermediate objects it depended on and which upstream results had to exist before it could be rebuilt.

This analysis connected the target reporting requirement to the original processing. It also exposed shared upstream models that should be reused across reports instead of regenerated separately.

Bronze, Silver and Gold responsibilities

Defined a layered target structure so that source representation, cleaning and business logic had distinct responsibilities. This made migration decisions explicit: which part of a procedural job belonged to source ingestion, which part prepared reliable data and which part expressed reporting logic.

LayerResponsibilityRelationship to verification
BronzeRepresent incoming source data one-to-oneEstablish that the conversion starts from the intended source records
SilverClean, type and deduplicate dataCheck the transformations that make data suitable for business use
GoldBuild facts, dimensions and reporting outputsCompare resulting business/reporting data with the existing reference output

Storage, processing, catalogues and development

The target design combined S3-compatible object storage with Spark processing and Delta Lake tables. I prepared PostgreSQL for local development and verification while retaining Spark as the target execution environment. Cross-platform checks mattered because successfully executing SQL in one engine was not proof that it behaved identically in another.

Turning procedural Oracle logic into dbt models

Developed patterns for decomposing Oracle PL/SQL processing into declarative SQL transformations. The conversion was organised around the intended output and its dependencies, rather than treating a large procedural script as one opaque object.

dbt models expressed the transformed relations, while Jinja2 supported repeatable patterns. The dependency analysis provided the build sequence: upstream models first, followed by the models that consumed them. The framework connected generated code with the original SQL and lineage needed to inspect a conversion.

The work also simplified the separate data-quality layer. Approximately 340 DQ table materialisations were removed from the migration pattern by incorporating their checks into processing. The quality rules remained part of the workflow while unnecessary intermediate materialisation was reduced.

Recovering dependencies from different kinds of evidence

Built Python tooling to analyse ODI sessions, Oracle job-chain definitions, regulatory processing patterns and Oracle view DDL. SQL parsing complemented metadata extraction because expressions and queries could reveal relationships that were not apparent from a job name or a table list.

Implemented seven dependency-resolution strategies to address different representations of dependencies in the source estate. The dependency analysis achieved 99.6% mapping coverage.

The analysed target batches included approximately 220 analytical and 190 regulatory tables. Dependencies were used to derive a topological build order, so migration could proceed through upstream prerequisites to the final targets.

From table lineage to inspectable column transformations

Reconstructed both table-level and column-level lineage. Table relationships explain which objects depend on one another; column derivations explain how an individual target field is produced, including the expressions involved.

Generated interactive HTML reports that exposed the related SQL and transformations. This gave engineers a way to inspect the transformation behind a dependency rather than relying on a diagram alone.

Exported structured JSON for downstream processing and loading into the AI knowledge base. The same recovered understanding could therefore support human review, model generation and documentation. Python, Groovy, sqlglot, Pydantic, pandas and Jinja2 were used across the analysis and reporting tooling.

Nine agents with separate responsibilities

Built a custom orchestration system around specialised agent roles. Separating the stages made it possible to identify whether a problem came from missing lineage, source data, generated SQL, execution or comparison with the reference.

The execution sequence

The orchestration used an explicit state machine: Extract → KB Load → Seed → Verify → Build, level by level → Final Verify → Commit. This kept analysis, preparation, generation and acceptance checks in a defined order.

  1. Extract the target’s lineage and the SQL needed to understand its dependencies.
  2. Load that context into the knowledge base and prepare the required source data.
  3. Verify Bronze inputs before downstream model generation.
  4. Build prerequisite models first, then move through successive dependency levels.
  5. Compile and execute generated transformations; inspect failures at the stage where they occur.
  6. Run final comparisons and retain the verified changes, diagnostics and documentation in the versioned delivery.

Verification involved running the SQL

Generated code was compiled and executed, and its resulting data was compared one-to-one with existing production reference outputs. A plausible SQL statement or successful compilation was therefore only an intermediate result.

Checks covered Bronze, Silver, Gold and relationships across models. The workflow needed both input checks and final output checks: an error at the source-representation stage could otherwise propagate through apparently valid downstream SQL.

Cross-platform verification supported the transition from PostgreSQL development to the Spark target. The practical outcome was a conversion process in which generated transformations could be investigated against the bank’s established results.

Handling failures without an uncontrolled repair loop

Implemented a fail-fast policy with one automated repair attempt. If the subsequent check still failed, the workflow escalated the problem for intervention. This bounded the repair process and kept repeated failures visible.

Added a watchdog, automatic restart handling and health-check endpoints for long-running orchestration. These operational components supported supervision of the process alongside the checks on the generated data.

Diagnosis and documentation were part of the same workflow, so a failed build could be investigated with its transformation context and verification outcome.

Parallel work, reuse and model selection

Supported parallel execution both between reports and within the dependency structure of a report. The execution order still followed prerequisites: parallelism applied where dependencies allowed it.

Detected shared models that had already been built for another report and reused them. This connected the dependency graph with practical orchestration, avoiding repeated generation of the same upstream work.

Used a tiered AI strategy: lower-cost processing for simpler, predictable tasks and more capable models for complex coordination. Claude AI, Python and a PostgreSQL knowledge base were components of the custom orchestration environment.

Delivery and engineering result

Handed the delivery team reusable migration patterns, models and pipelines, together with the lineage analysis and verification approach. Interactive reports, structured metadata, model outputs and documentation connected the architecture to the work needed to continue implementation.

The contribution covered the full engineering chain: understanding a large legacy estate, expressing its logic in a new architecture, generating transformations in the required order and checking actual results. The measurable source figures, coverage and DQ simplification belong to those specific workstreams; they are not presented as a completed migration of the entire bank.
