Project in depth

From legacy ETL to an open lakehouse

Designed the migration architecture and built the tools needed to understand, convert and verify legacy ETL at Raiffeisenbank Austria d.d. in Croatia. The work combined data modelling, automated lineage analysis, AI-assisted SQL conversion and checks against the bank’s existing results.

Client / context
Raiffeisenbank Austria d.d., Croatia (RBA)
Period
September 2025 – February 2026
My role
Data Architect / Principal Data Engineer

Understanding the existing warehouse

The source estate contained approximately 4,300 ETL mappings, 1,800 landing tables and more than 20 source systems. Logic was spread across Oracle Data Integrator, Oracle Job Chains, IBM DataStage, PL/SQL and database views. These figures describe the source estate addressed by the migration framework.

Analysed how operational data moved through landing, staging, data-quality, core, view and reporting layers. The practical question was which source fields and transformations were needed to reproduce each business or regulatory output.

Reconstructing table and column lineage

Built Python tools that read metadata, job definitions and SQL to reconstruct input/output dependencies. Implemented seven resolution strategies to handle different ways in which jobs and database objects expressed those dependencies.

Parsed transformations and expressions to follow both table relationships and column derivations. Generated interactive HTML reports with the underlying SQL and structured JSON for further processing. The dependency graph also determined the order in which dbt models should be built.

Designing the target lakehouse

Defined Bronze as a one-to-one representation of incoming data, Silver for cleaning, typing and deduplication, and Gold for business facts, dimensions and reporting. Developed reusable dbt and Jinja2 patterns to turn procedural Oracle logic into declarative models.

Prepared PostgreSQL for local development and verification, with Spark and Delta Lake as the target processing and table layers. The architecture included MinIO for S3-compatible storage, Hive Metastore, Kyuubi for JDBC access to Spark, and Airflow for orchestration.

Coordinating nine specialised AI agents

Built an orchestration system that assigned separate tasks to lineage retrieval, knowledge loading, data preparation, Bronze verification, model generation, compilation, cross-platform validation, diagnosis and documentation.

Organised execution as extract, knowledge loading, seed preparation, verification, dependency-ordered model builds and final verification. Reused models already built for another report and supported parallel work where dependencies allowed it.

Checking generated SQL against real results

The workflow compiled and executed the generated SQL and compared its results with existing production reference outputs. Bronze, Silver and Gold checks were part of the conversion process.

When a check failed, the system attempted one automated repair and escalated a repeated failure. Added health checks, a watchdog and restart handling to monitor long-running work. Deterministic tasks used simpler processing while complex coordination used a more capable model.

Simplifying quality checks and handing over the framework

Removed the need for approximately 340 separately materialised data-quality tables by incorporating their checks into the new processing approach. This reduced unnecessary intermediate storage and simplified the migration pattern.

Handed over reusable migration patterns, models and pipelines to the delivery team, together with traceable analysis, diagnostics, documentation and versioned changes.
