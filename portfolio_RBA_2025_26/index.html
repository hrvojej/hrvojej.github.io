From legacy ETL to an open lakehouse

Built tools to analyse the bank’s existing ETL jobs, trace how source data became reports, and convert legacy transformations into dbt models for an open lakehouse.

The problem and my responsibility

The source warehouse combined Oracle and PostgreSQL, approximately 4,300 ETL mappings, 1,800 landing tables and more than 20 upstream systems. Transformation logic was distributed across Oracle Data Integrator, job chains, IBM DataStage, PL/SQL and database views.

Led the technical work across legacy-system analysis, target data modelling and migration verification. Reconstructed existing transformation logic, expressed it as reusable lakehouse models and checked converted results against production reference outputs.

1. Reverse engineering and table/column lineage

Developed a Python-based platform to reconstruct dependencies from ODI sessions, Oracle Job Chains, regulatory reporting definitions and view SQL. The analysis linked inputs and outputs across landing, staging, data-quality, core, view and target layers.

Implemented seven dependency-resolution strategies for different object definitions and orchestration patterns. Parsed expressions and transformations to expose both table-level dependencies and column-level derivations, retaining the SQL needed to explain a result.

Generated HTML reports showing the SQL, source tables and transformation logic behind each output. Exported the same information as JSON for automated conversion. Used model dependencies to determine which inputs had to be built before the models that relied on them.

  • Analysed ODI, OJC, DataStage, Oracle, PostgreSQL and PL/SQL metadata.
  • Connected business outputs to source fields and intermediate transformation logic.
  • Prepared batch analysis for approximately 220 analytical and 190 regulatory target tables.
  • Used Python, Groovy, sqlglot, Jinja2, Pydantic and pandas for parsing and structured outputs.

2. A portable lakehouse migration framework

Designed three data layers: Bronze retained source records, Silver cleaned and deduplicated them, and Gold organised them into business facts, dimensions and reporting models.

Developed reusable dbt patterns for translating Oracle PL/SQL logic into declarative SQL models. PostgreSQL supported local development and verification, while Apache Spark was the target execution platform. This separated the reusable model pattern from engine-specific implementation details.

The architecture combined S3-compatible MinIO storage, Delta Lake for the transactional data layer, Hive Metastore for metadata, Kyuubi for JDBC access to Spark and Airflow for orchestration. Git and Jinja2 supported repeatable development and controlled changes.

Removed the need for approximately 340 separately stored data-quality tables by running the quality checks within the new processing flow. Prepared the framework for a move from licensed tooling to an open-source platform.

3. AI orchestration with explicit verification

Designed and implemented an orchestration engine with nine specialised agents: lineage extraction, knowledge-base loading, data preparation, Bronze verification, model construction, compilation, cross-platform verification, diagnosis and documentation.

The state-machine flow was Extract → KB Load → Seed → Verify → Build by dependency level → Final Verify → Commit. Previously constructed shared components could be reused, while independent reports and models could execute in parallel.

Legacy Oracle/PL/SQL was translated into dbt SQL, compiled, actually executed and compared with reference production outputs. Verification covered Bronze, Silver and Gold and the relationships between models. A failed check triggered one automated repair attempt, followed by escalation when the problem remained unresolved.

Added watchdogs, state checks and restart mechanisms. Separated inexpensive deterministic work from more complex model-driven tasks, with a PostgreSQL knowledge base, Python orchestration and Git versioning.

Reusable migration patterns and team handover

Handed over migration models and pipelines to the delivery team for continued execution. The framework combined source discovery, lineage, dependency ordering, transformation, verification and diagnosis in a repeatable process.

Retained source SQL and transformation context alongside generated models so the team could trace business outputs and investigate differences. AI-assisted conversion operated within compilation, execution and reference-output checks.
