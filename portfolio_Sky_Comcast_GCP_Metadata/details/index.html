Project in depth

Sky / Comcast: schema-metadata capture on Google Cloud

Designed, implemented and tested a prototype for capturing database-schema metadata changes in Google Cloud AlloyDB. Built metadata tables, refresh logic and change-audit functions as the basis for making table and column information available to the Dataplex governance environment.

Client / context
Comcast / Sky Group / Sky UK · via Intuita Consulting
Period
During the Intuita engagement · September 2022 – February 2024
My role
Lead Engineer / Developer

Purpose and scope of the prototype

Sky wanted technical metadata about schemas, tables and columns from AlloyDB to be usable in Dataplex, where governance information could be associated with those objects. I led the prototype engineering and testing during the Intuita engagement.

The central subject was metadata about database structures. A column being added or removed is a different event from a customer record being updated; the implemented metadata capture is described here on that basis.

Building metadata tables from the database catalogue

Created separate table and column metadata relations from information_schema.tables and information_schema.columns. The selection excluded system schemas, platform-internal objects and the metadata tables themselves.

The table metadata describes the database objects, while the column metadata retains their field definitions and properties. Keeping these structures separate supports both table-level discovery and more detailed column-level governance.

Refreshing metadata after DDL changes

Implemented a PL/pgSQL refresh function and attached it to a ddl_command_end event trigger. In the full-refresh variant, the function rebuilds the metadata tables from the current catalogue after a schema operation.

Prepared test operations that create a table and add or remove a column, then inspect metadata-table counts and contents. The working notes record successful testing of this refresh behaviour.

Full refresh and incremental processing were considered as different implementation choices. The demonstrated refresh mechanism and the audit functions have separate responsibilities; their presence alone does not imply a production catalogue-sync service.

Recording changes in audit tables

Built table- and column-metadata audit tables and PL/pgSQL trigger functions. The functions handle INSERT, UPDATE and DELETE, retaining the operation, affected metadata table, timestamp and old/new row representation as appropriate.

OperationRecorded content
INSERTThe new metadata row
UPDATEBoth old and new metadata rows
DELETEThe previous metadata row

Cloud integration and verification

Worked with Python, SQL, PostgreSQL and the AlloyDB cluster in a GCP environment that also included Dataplex, BigQuery, Cloud Storage and Cloud Tasks. The wider design connected change capture with the cloud catalogue and analytical ecosystem.

Tested schema-change handling and the integrity of the captured metadata in the prototype. Prepared database inspection and trigger/function checks to make the behaviour observable during development.

Engineering output

The work produced a tested prototype, metadata structures, refresh and audit logic, and an integration approach for governance. It showed how database changes could become structured information for catalogue processing, with the implementation status kept distinct from a full operational deployment.
